# Hermeticity

This file lists each input of the Node build and where it comes from.
The build is not fully hermetic. The gaps are named here.

## Rungs

Each input has a rung. A lower rung is stronger.

| Rung | Meaning |
|---|---|
| 0 | Pinned address and pinned checksum |
| 1 | Pinned checksum, with the checksum computed here from a download |
| 2 | Generated by a named tool |
| 6 | Stays on the host |

I computed the LLVM checksums from the downloads.

## Host inputs

### macOS SDK

The Apple SDK license does not allow a pinned copy in a public repository.
`bazel/sdk.bzl` selects an SDK from the host.
It writes the path, the version, and a digest of `SDKSettings.json` to `info.json`.
The build action reads `info.json`, so a new SDK makes a new cache key.
The tarball records the same values in `BUILDINFO.json`.
A change to an SDK file with no change to `SDKSettings.json` does not make a new key.

Set `ROOTBEER_MACOS_SDK` to select a different SDK.

`ld64.lld` 19 cannot read a `.tbd` file that lists `arm64e.x1`.
`bazel/sdk.bzl` skips an SDK with this architecture.
A host that has only such an SDK fails with a clear message.

### POSIX tools

The action `PATH` holds the tool wrappers, then `/usr/bin`, then `/bin`.
Node's configure and build steps call `sh`, `sed`, `cp`, `mkdir`, and similar tools.
These tools come from the host.
The result does not record their versions.

### Sandbox limits

The Bazel sandboxes on macOS and Linux do not hide host read paths.
A step can still read `/usr/include` or `/usr/lib` if a flag points there.
The Bazel sandbox removes the environment and limits write paths.
It does not prove that the build reads only declared inputs.

The evidence for this claim is narrower:

- `LinkCheck.test_only_system_libraries` reads the needed libraries of the binary.
- The compiler gets `-isysroot` or `--sysroot`, and `-nostdinc++`.
- The Linux build runs in a container with no host compiler.

## Linked libraries

The macOS binary links these libraries only. Some lines link fewer.
For example, the Node 18 binary links only `libSystem.B.dylib` and CoreFoundation.

- `libSystem.B.dylib`
- `libobjc.A.dylib`, when a framework needs it
- CoreFoundation and Security frameworks

libc++ and libc++abi link statically.

The Linux binary links glibc libraries and `libgcc_s` only.
These libraries come from the host at run time.
The sysroot sets the glibc floor at version 2.31.

## Known limits

- `-Wl,-no_fixup_chains` is required on macOS.
  A binary with static libc++ and chained fixups crashed at startup with exit code 139 on Darwin 27.
  I did not find the root cause. This is an observation and not an explanation.
- The LLVM libc++.a objects target macOS 14.0, and the linker warns about this.
  The practical minimum for the macOS artifacts is macOS 14.
- The build does not prove byte-for-byte reproducibility.
  The driver sets `SOURCE_DATE_EPOCH`, `ZERO_AR_DATE`, and `-ffile-prefix-map`.
  No test compares two builds.
- Node's `OPENSSLDIR` value comes from Node's own OpenSSL configuration.
  It is `/etc/ssl` on macOS and on Linux. This is a host path by design.

## Linux container

`docker/Dockerfile` supplies Bazel, the POSIX tools, and a CA store.
The base image is pinned by digest, and the Bazel binary is pinned by checksum.
`apt-get` packages in that image are not pinned.
They run tools only. The image holds no compiler.

The pinned LLVM Linux tools are dynamic programs.
They load `libstdc++`, `libz`, `libzstd`, and `libxml2` from the image.
`ld.lld` fails with a missing `libxml2.so.2` error when the image does not supply it.
These libraries are rung 6 inputs. Their versions are not recorded.
