# Hermeticity

This file lists each input of the Node build and where it comes from.
The build is not fully hermetic. The gaps are named here.

## Rungs

Each input has a rung. A lower rung is stronger.

| Rung | Meaning |
|---|---|
| 0 | Pinned address and pinned checksum |
| 1 | Pinned checksum, with the checksum computed here from a download |
| 2 | Generated by a named tool |
| 6 | Stays on the host |

## Host inputs

### macOS SDK

The Apple SDK license does not allow a pinned copy in a public repository.
`bazel/sdk.bzl` selects an SDK from the host.
It writes the path, the version, and a digest of `SDKSettings.json` to `info.json`.
The build action reads `info.json`, so a new SDK makes a new cache key.
The tarball records the same values in `BUILDINFO.json`.
A change to an SDK file with no change to `SDKSettings.json` does not make a new key.

Set `ROOTBEER_MACOS_SDK` to select a different SDK.

`ld64.lld` 19 cannot read a `.tbd` file that lists `arm64e.x1`.
`bazel/sdk.bzl` skips an SDK with this architecture.
A host that has only such an SDK fails with a clear message.

### POSIX tools

The action `PATH` holds the tool wrappers, then `/usr/bin`, then `/bin`.
Node's configure and build steps call `sh`, `sed`, `cp`, `mkdir`, and similar tools.

- **Linux:** The build image supplies these tools. They are BusyBox, pinned by checksum (rung 0).
- **macOS:** These tools come from the host. The result does not record their versions (rung 6).

### Sandbox limits

The Bazel sandboxes on macOS and Linux do not hide host read paths.
A step can still read `/usr/include` or `/usr/lib` if a flag points there.
The Bazel sandbox removes the environment and limits write paths.
It does not prove that the build reads only declared inputs.

The evidence for this claim is narrower:

- `LinkCheck.test_only_system_libraries` reads the needed libraries of the binary.
- The compiler gets `-isysroot` or `--sysroot`, and `-nostdinc++`.
- The Linux build runs in a container with no host compiler.

## Linked libraries

The macOS binary links these libraries only. Some lines link fewer.
For example, the Node 18 binary links only `libSystem.B.dylib` and CoreFoundation.

- `libSystem.B.dylib`
- `libobjc.A.dylib`, when a framework needs it
- CoreFoundation and Security frameworks

libc++ and libc++abi link statically.

The Linux binary links glibc libraries and `libgcc_s` only.
These libraries come from the host at run time.
Node passes `-latomic` to the linker on Linux with Clang.
`MODULE.bazel` removes `libatomic.so` from the sysroot, so the linker selects `libatomic.a`.
The sysroot ships glibc 2.31, so the binary cannot import a newer symbol.
`GlibcFloor` in `tests/hermetic_test.py` fails when any imported symbol needs glibc newer than 2.31.
The measured floor of the current builds is glibc 2.25.

## Known limits

- `-Wl,-no_fixup_chains` is required on macOS.
  A binary with static libc++ and chained fixups crashes at startup with exit code 139 on Darwin 27.
  This program is enough to show it, with no Node code:
  `#include <iostream>` and `int main() { std::cout << 1; }`,
  compiled with the pinned clang and `-nostdlib++`, and linked with the pinned `libc++.a` and `libc++abi.a`.
  - The crash is a call through a null pointer in `std::__1::__stdinbuf<char>::imbue`, from `DoIOSInit`.
  - `dyld_info -fixups` shows the vtable slots of the libc++ weak definitions as chained binds to
    `<weak-def-coalesce>/<symbol>`. The symbols are in the export trie of the executable, flagged weak.
    The binary has 687 such binds, and dyld 27 leaves these slots null.
  - Apple's `ld` makes the same crashing binary, so the pinned lld is not the cause.
  - `-Wl,-no_exported_symbols` removes the binds and the crash with chained fixups on, with `ld` and with lld.
    It is not usable, because native add-ons resolve the Node and V8 symbols from the executable.
  - `-Wl,-no_fixup_chains` keeps the classic weak-binding opcodes, and it works.
  - Stock Node does not meet this, because it uses the libc++ of the system.
  - I did not test other macOS versions. The flag is correct on all of them, and the cost is a larger relocation table.
- The LLVM libc++.a objects target macOS 14.0, and the linker warns about this.
  The practical minimum for the macOS artifacts is macOS 14.
- The build does not prove byte-for-byte reproducibility.
  The driver sets `SOURCE_DATE_EPOCH`, `ZERO_AR_DATE`, and `-ffile-prefix-map`.
  No test compares two builds.
- Node's `OPENSSLDIR` value comes from Node's own OpenSSL configuration.
  It is `/etc/ssl` on macOS and on Linux. This is a host path by design.

## Linux container

`docker/Dockerfile` makes a small image that holds only pinned files.
It has no package manager, no shell other than BusyBox, and no compiler.

| Input | How it is pinned |
|---|---|
| Unpack stage | `FROM` image with a `@sha256:` digest. It runs `dpkg-deb -x` and `ln` only. |
| Final stage | `FROM scratch`. Only `COPY` adds files. |
| Bazel | `ADD --checksum=sha256:`. This binary has its own JDK. |
| BusyBox and libraries | One `ADD --checksum=sha256:` for each `.deb`. |
| `.deb` address | `snapshot.debian.org/archive/debian/<timestamp>/`. The address cannot change. |
| CA bundle | `COPY trust/mozilla-no-emsign.pem`. It is the pinned test bundle of this repository. |
| `passwd`, `group`, `nsswitch.conf` | `docker/etc/` in this repository. |

The packages are `libc6`, `libgcc-s1`, `libstdc++6`, `zlib1g`, `libzstd1`, `liblzma5`,
`libxml2`, `libicu72`, `libtinfo6`, `bash`, `dash`, and `busybox-static`. The pinned LLVM Linux tools load these libraries.
`ld.lld` needs `libxml2`, `libicu72`, and `liblzma5`. The other tools need `libstdc++`, `libz`, and `libzstd`.

`tools/pin_debs.py` prints the `ADD` lines for a snapshot timestamp.
A reviewer can run it again and compare the checksums.
This tool is the only step that reads an index that is not pinned. The build never runs it.

`tests/docker_test.py` fails the build when a `FROM` has no digest,
an `ADD` has no checksum, a `.deb` does not come from the snapshot archive,
or a `RUN` calls `apt`, `curl`, or another tool that fetches inputs.

BusyBox has no `find -delete` and no `bash`.
`MODULE.bazel` uses `find -exec rm -f {} +`.
The image has GNU `bash` from a pinned `.deb`, because Bazel runs `patch_cmds` and its test scripts with `bash`.
A BusyBox `sh` runs its own applets before it looks at `PATH`.
That hides a wrapper with the same name, for example `ar`.
For this reason `/bin/sh` is `dash`, and the image has no `ar` link.

### Remaining Linux gaps

- Docker, the kernel, and the CPU come from the host.
- The Bazel sandbox inside Docker is `processwrapper-sandbox`. It does not hide host read paths.
- BusyBox applets have different options than GNU tools. A new build step can need a GNU option.
- `snapshot.debian.org` is a single host. The checksums stop a changed file but cannot stop an outage.
- No test compares two builds, so the image content is not proven reproducible byte for byte.
